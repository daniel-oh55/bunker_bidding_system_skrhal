# Security Model

## Core rules

- No real secret values are stored in the repository.
- Browser code uses only the Supabase publishable key.
- Secret values and backend credentials never enter browser code, Vite variables, repository source values, logs, or test output. Symbolic runtime names are confined to server-only Edge Function files.
- Authorization never trusts `user_metadata` or other unverified client claims.
- Suspended or inactive users immediately lose access.
- Verified membership in an active organization is the basis for current access decisions.
- Authentication alone never grants business authorization, and application filtering is not an authorization boundary.

- Account, organization, and membership status are evaluated in PostgreSQL, not from JWT metadata.
- Private authorization tables live in the non-exposed `app_private` schema with RLS enabled and direct `anon`/`authenticated` table privileges revoked.
- `public.current_access_context()` is executable only by `authenticated` callers and returns only the caller's active memberships through security-definer functions with fixed search paths. Its trimmed organization label comes from the verified active organization row and is presentation data, never authority.
- The sign-in-only frontend calls that RPC after initial session hydration and after Auth state changes. It authorizes the shell only when at least one context is returned.
- The state machine immediately clears contexts on sign-out, ignores stale RPC results, distinguishes zero-context denial from transient errors, and preserves multiple active memberships.
- Missing browser configuration fails closed. The browser client is never partially configured and accepts only the URL and publishable key.
- The loopback-only integration harness isolates elevated local access to fixture preparation and cleanup; its sign-in and RPC checks use the publishable client.
- The frontend creates separate access, bidding, and narrow Realtime invalidation adapters from the same publishable client and never exposes the raw client to components. The bidding adapter exposes mail intake list/dismiss but no ingest method. It selects only server-returned memberships, validates every RPC response before rendering, and clears protected data before an authorization-failure recheck. The sanitized access session contains only email and the authenticated user UUID needed to form that user's own access topic; it contains no token, raw User, metadata, or claims. This is UX/state coordination, not the enforcement layer; bid, quote, and mail-intake data still require RLS or server-side functions.
- SELLER is a user-facing label for the existing TRADER organization security identity. A dedicated fixed-search-path `SECURITY DEFINER` helper requires the authenticated user, submitted membership, active account, active membership, active BUYER organization, and stored `buyer_admin` role. The existing generic active-BUYER helper is unchanged, so `buyer_operator` keeps normal bidding authority but cannot list, create, or deactivate SELLER masters.
- The SELLER admin list returns only organization ID/label/status, active TRADER-membership count, and timestamps. Create trims and bounds the name and inserts only an active TRADER organization. A partial unique index on `lower(btrim(name))` for `kind = trader` reserves normalized identity across inactive and suspended rows while leaving BUYER names unchanged. Neither client roles nor UI visibility authorize these actions.
- Deactivation locks the target row, permits only active-to-inactive, treats inactive as idempotent, and rejects suspended. It retains memberships, BID scope, quotes, awards, and history. No delete, reactivate, rename, or generic status-update RPC is present; retained old BID scopes create a deliberate future scope-revival hazard that must be resolved before any reactivation authority is designed.
- The private SELLER-admin audit table is RLS-enabled with direct public/anon/authenticated access revoked and an elevated update/delete rejection trigger. Reviewed server functions append one created event and at most one deactivated event per organization, recording the verified BUYER-admin actor and exact bounded organization ID/label/status snapshots only. No email, Auth credential, secret, or membership-private snapshot is stored.
- SELLER creation calls the existing private BUYER workspace invalidation helper. Deactivation uses the existing organization update trigger, which sends access invalidation to all retained members and one BUYER workspace invalidation. Payloads remain data-free kind markers and never carry SELLER identity. The selected membership role controls frontend presentation only; admin RPC authorization remains entirely server-side.
- The BUYER-only manual `.msg` intake treats local files as untrusted input. It checks one case-insensitive `.msg` name, a 5 MiB limit, and the CFBF signature before parsing; catches parser failures into fixed UI errors; and exposes only normalized plain-text subject/body to the business parser. It neither uploads nor persists files/content, logs raw content, extracts or renders attachments/HTML, nor fetches referenced resources.
- Parsed values are non-authoritative candidates with warnings. Apply is explicit and can change only usable vessel/voyage, port, delivery, and supported fuel candidates in the visible form. It never changes the deadline or responsible BUYER and never invokes an RPC, Auth recheck, list reload, Realtime operation, or server endpoint. The unchanged explicit Create bid submission remains the only route to the authoritative server RPC.
- The server-side mail intake queue is private and RLS-enabled. Its elevated connector role has no direct SELECT/INSERT/UPDATE/DELETE and, among the three public mail-intake RPCs, can execute only fixed-search-path `SECURITY DEFINER` ingest; list and dismiss are denied. Ingest accepts no actor membership or credential/address/raw-message fields, and browser code never receives elevated or provider credentials.
- Intake source identity is exactly the normalized provider, opaque mailbox key, and message ID under a unique database constraint. Ingress uses that constraint as the authoritative concurrency boundary, returns the existing internal UUID on duplicates, and never overwrites or reopens the stored row. Deterministic READ COMMITTED tests cover both a first-writer commit and rollback after the second ingest is observed waiting on the unique index.
- Authenticated intake reads and dismissals are available only through narrow fixed-search-path RPCs that call `app_private.require_active_buyer_actor()`. All active approved BUYERs share pending visibility; active TRADERs, inactive account/membership/organization states, forged membership IDs, anonymous callers, and client metadata fail closed. Dismissal locks the row, requires its expected revision, records the actual authenticated user and verified membership, increments once, and has no restore operation.
- Intake storage contains bounded normalized subject/candidate/warning data only. Raw body, HTML, attachments, sender/recipient/address fields, mailbox credentials, deadline, responsible BUYER, bid conversion, and bid creation are absent; source mailbox and message identifiers are excluded from BUYER RPC results.
- The active Production Gmail Edge Function is server-to-server only. Platform JWT verification remains intentionally disabled; it accepts POST and requires the exact dedicated trigger header before IMAP, database RPC, or cursor access, so a browser JWT grants no connector authority. Runtime configuration uses server-side Gmail IMAP and trigger secrets, with no values committed or logged.
- The Gmail connector uses only IMAP with an App Password at fixed `imap.gmail.com:993` TLS. It opens only `INBOX` read-only and exposes no flag, move, copy, delete, folder, or long-lived IDLE operation. OAuth, Gmail API, raw MIME, attachment fetch, HTML parsing, address extraction, and URL following are absent. Before body download or parsing, the original envelope subject must begin at its first character with the exact case-sensitive ASCII prefix `//SPOT//`; reply prefixes, leading whitespace, wrong case, and later occurrences are filtered without ingest or absent/error classification. Eligible inline plain text is decoded under a 256 KiB aggregate limit and kept only long enough to produce the bounded advisory ingest payload through the existing parser; the stored normalized subject retains the marker while parser subject input omits that leading marker and following whitespace. Controlled Gmail/App Password setup and live mailbox connectivity are complete, while credentials remain server-side and must never be committed.
- The private cursor table contains no address, message, subject/body, or credential data. RLS has no policies, direct CRUD is denied to `PUBLIC`, `anon`, `authenticated`, and the backend connector role, and only the two fixed-search-path cursor RPCs are executable by that role. Initialization and advancement are CAS operations using strict `imap-v1:<uidvalidity>:<last_uid>` values; conflicts use SQLSTATE `40001`. UIDVALIDITY change and all retrieval/processing failures except a definitive missing UID in the captured snapshot do not reset or advance state. That terminal absence is not ingested or identified in the response, and after all other messages succeed its bounded aggregate count may accompany a CAS advancement. No historical mailbox scan is available.
- Password reset requests use the Supabase Auth client with this application's origin/root as the redirect target and return generic feedback. `PASSWORD_RECOVERY` sessions are not business authorization: they preempt access RPCs, ignore other Auth events until completion or sign-out, and never render protected workspace content.

## Enforced bidding and scope rules

- Public signup remains disallowed and has no frontend control.
- approved BUYER accounts may number three or more
- every approved BUYER can see all bids and all quotes
- BUYER views support all bids, bids created by the current BUYER, and filtering by BUYER
- TRADER access requires verified membership in an approved organization and is limited to explicitly allowed bid and quote scope.
- `created_by` is immutable and remains separate from the actor performing update, close, reopen, award, or cancel operations
- Deadlines use server time.
- Quote creation and modification after close are rejected server-side.
- Close, reopen, award, and cancel are server-side transactional operations.
- Active BUYERs may perform cross-BUYER changes through the server RPCs; those changes never rewrite `created_by` and audit the actual actor. Responsibility is a visibility filter, not authority.
- Privilege tests may use elevated fixture setup, but allowed and denied behavior run under the target caller role.
- Provider-originated `received_at` is source metadata only and never bidding deadline authority; intake cannot infer a deadline or responsible BUYER and cannot call the bid creation RPC.
- The mail-intake, cursor, and polling-extension migrations are applied in Production. PR #34 exposes only provider-neutral pending list/dismiss to the active-BUYER frontend, with target-and-revision confirmation, authoritative reloads, authorization clearing, and stale-result rejection. The active Gmail connector's ingest serialization retry is capped at three attempts and cursor conflicts are never retried into an overwrite. Intake remains review-only: no automatic historical import, bid creation, or intake-to-bid conversion exists, and TRADERs have no mail-intake access.

The integrated frontend workspace does not grant authority and does not request competitor data from a TRADER context. It presents the server organization label without using it as identity or authority; acceptance of the old four-field RPC shape and its shortened neutral-ID display exists solely for safe rollout ordering. It uses manual refresh and post-mutation server reload as durable fallback paths. Its private Realtime consumer accepts only exact marker kinds: `access_changed` calls `current_access_context()` before protected access continues, while `workspace_changed` invokes the existing selected BUYER/TRADER authoritative reload. Production verification observed the authorized BUYER and selected TRADER reload paths, preserved non-scoped and competitor isolation, and caused a controlled inactive membership to lose its workspace with no active authorized membership. Realtime cannot grant or broaden authorization: delivery failure or absence never grants authority, and stale callbacks/results cannot restore obsolete data. No real operational bidding data has been migrated or is in use; retained Production records are synthetic smoke records only.
